## 一、项目介绍（三个版本，按时间控制）

**30 秒版（一句话）**

> 我独立开发了一个运维知识库问答系统：用 LangChain 搭 RAG 流水线，
> 把 MySQL 里的运维文档向量化存入 Milvus，用户提问先检索相关文档再让通义千问作答，
> Redis 缓存热点问题，FastAPI 提供接口和 Web 页面，Docker Compose 一键部署。

**2 分钟版（讲链路）**

> 数据层：MySQL 存原始知识文档（27 篇、3 个分类），文档切块后向量化写入 Milvus。
> 检索层：问题向量在 Milvus 里做相似度检索，取 top-3 文档。
> 生成层：检索结果 + 问题组装进 prompt，交给通义千问，prompt 里强制「资料里没有就直说不知道」，
> 并在响应里返回 sources 溯源。
> 性能层：Cache Aside 模式，相同问题直接 Redis 命中，实测从 3.7 秒降到 0.13 秒，且不重复调付费模型。
> 工程层：pytest 接口测试全 mock 外部依赖，Docker Compose 编排四个服务并带健康检查。

**5 分钟版**：把下面「项目故事线」按阶段展开讲。

## 二、项目故事线（按开发顺序讲，体现工程思维）

1. **先建模**：SQLAlchemy ORM 设计 categories / knowledge_docs 两张表，
   种子脚本做幂等（插入前查重），跑多少次都不产生重复数据。
2. **再索引**：文档切块（chunk_size + overlap 防切断语义），用 text-embedding-v3 向量化写入 Milvus；
   关键经验：写入端开了动态字段，读取端也要开，否则元数据（标题/分类）查不回来。
3. **搭 RAG**：LCEL 流水线 `{context: retriever | format, question: passthrough} | prompt | llm | parser`；
   防幻觉靠系统提示词强约束。
4. **封接口**：FastAPI + Pydantic，lifespan 启动时加载一次向量库和链路（全局复用）；
   同步 def 接口由 FastAPI 自动丢线程池，不阻塞事件循环。
5. **加缓存**：Cache Aside、SHA256 哈希 key、TTL 被动过期；
   数据重建时主动清缓存（`clear_cache`），Redis 故障时 try/except 降级直连。
6. **做前端**：原生 JS fetch 调接口，转义 HTML 防 XSS，发送期间双锁防重复提交。
7. **写测试**：monkeypatch mock 掉大模型，缓存命中测试断言「没有调用模型」。
8. **容器化**：Docker Compose 编排 + 健康检查 + 数据卷，数据库端口不对外暴露。

## 三、高频面试题（按主题，含参考答案要点）

### RAG 相关

**Q1：为什么用 RAG 而不是直接把知识喂给大模型？**
答：大模型有上下文窗口限制，塞不下整个知识库；且模型记忆会过时、会幻觉。
RAG = 先检索最相关的几篇文档，再让模型「开卷作答」——成本低（每次只送几段）、可更新（改知识库即可）、可溯源（返回 sources）。

**Q2：怎么防止幻觉？**
答：三层：① prompt 强约束「无资料即答不知道」；② 只把检索到的资料作为上下文；③ 响应带 sources 让用户核对。
测试里我专门问了知识库外的问题，确认模型回答「知识库中没有相关内容」。

**Q3：chunk_size 和 chunk_overlap 怎么定？**
答：chunk_size 取决于文档长度、检索粒度和模型上下文预算；overlap 防止切分把关键句拦腰截断。
我的种子文档短所以切得小（150 字符 + 30 重叠）；真实项目通常 300~500 字符，并要做实验调参。

**Q4：怎么评估 RAG 好不好？**
答：拆成两段评估：检索质量（top-k 是否命中正确答案，可用命中率/召回率）和生成质量
（回答是否准确、有无幻觉）。进阶做法是建一批问答测试集跑指标。

### 向量库 / Milvus 相关

**Q5：为什么选 Milvus 而不是 Chroma/FAISS？**
答：Milvus 是生产级分布式向量数据库，支持动态字段、过滤、副本、大规模数据，
更贴近真实业务；同时我通过 Docker 部署它，也练习了容器化。Chroma 适合个人原型，FAISS 是库不是服务。

**Q6：写入和读取时动态字段配置不一致会怎样？（真实踩坑）**
答：我遇到过：写入时开了 enable_dynamic_field=True，数据确实存进去了；
但读取端创建 Milvus 对象时漏了这个参数，检索结果只返回主键，标题等元数据全丢。
教训：读写两端配置必须一致。

**Q7：向量相似度用什么度量？**
答：常用余弦相似度（看方向）和 L2 距离（看绝对距离）。我当前用默认配置，
分数是距离（越小越接近）；换余弦时要注意分数越大越相似，排序逻辑要对应调整。

### Redis / 缓存相关

**Q8：Cache Aside 是什么？为什么先更新数据库再删缓存？**
答：读：先查缓存，未命中查库并回填。写：先更新库，再删缓存。
如果先删缓存再写库，中间有并发读会把旧值回填，缓存里就长期是脏数据。
（追问：极端并发仍可能脏读，可用延迟双删/版本号。）

**Q9：缓存 key 为什么用哈希？**
答：问题文本可能很长且有中文、空格等特殊字符，直接做 key 浪费内存且易出错；
SHA256 哈希成固定长度十六进制，还隐藏了原始问题。

**Q10：缓存一致性怎么保证？**
答：TTL 被动过期兜底 + 知识重建时主动清缓存（我在 indexer 重建向量库后调用 clear_cache）。
进阶方案：key 带版本号，更新时版本 +1，旧缓存整体作废。

**Q11：缓存穿透/击穿/雪崩是什么？你的系统怎么防？**
答：穿透=查不存在的 key 打到数据库 → 布隆过滤器/缓存空值；
击穿=热点 key 过期瞬间并发打库 → 互斥锁/逻辑过期；
雪崩=大量 key 同时过期 → 随机过期时间/多级缓存。
我的系统用 TTL 和主动失效，问答场景下问题天然分散，风险相对低，但原理要能讲清。

**Q12：Redis 挂了你的接口会怎样？**
答：会降级而不是崩溃。读缓存用 try/except，异常当未命中走完整 RAG；写缓存失败只告警不影响返回。
代价是慢一点、多花一次模型调用，但系统可用。

### MySQL / 数据相关

**Q13：两张表怎么设计的？为什么用外键？**
答：categories（分类）与 knowledge_docs（文档）一对多，外键保证引用完整性，
ORM 里 relationship 可以对象级联查。文档表字段含标题、正文、标签、来源、时间戳。

**Q14：脚本为什么能重复跑？**
答：幂等设计：建库用 IF NOT EXISTS，建表 create_all 只补缺失表，
插入前按 name/title 查重；向量库重建用 drop_old=True（重建式幂等）。

### FastAPI / 工程相关

**Q15：同步 def 和 async def 接口有什么区别？**
答：def 会被 FastAPI 丢进线程池执行，适合 IO 阻塞型业务（调数据库/大模型）；
async def 跑在事件循环里，适合本身异步的操作。我选 def，让 FastAPI 管线程，避免阻塞事件循环。

**Q16：为什么服务启动时才加载向量库和链路？**
答：资源复用——Milvus 连接和大模型客户端是重量级资源，启动初始化一次、
全局复用，比每个请求重新连接快得多（类比餐厅开张备好厨房，而不是每桌现买厨具）。

**Q17：错误处理怎么做？**
答：全局 exception_handler 兜底返回友好 JSON；Redis 等非核心依赖 try/except 降级。
参数校验交给 Pydantic（空问题返回 422）。

**Q18：前端怎么防 XSS？**
答：用户输入和大模型输出一律先 escapeHtml 转义，再做 **加粗** 等格式转换；
插用户消息用 textContent（天然不解析 HTML）。

**Q19：测试怎么不花钱不依赖外部服务？**
答：monkeypatch 把 ask（大模型）换成假函数；用 FakeVectorStore 替 Milvus；
缓存命中测试里把 ask 换成「调用即抛错」的函数，断言缓存命中时确实没调模型。

### Docker 相关

**Q20：Compose 里服务之间怎么通信？健康检查有什么用？**
答：同网络内用服务名（mysql/redis/milvus）互相访问；
healthcheck + depends_on condition 保证应用在依赖就绪后才启动，避免启动竞态。

## 四、容易被追问的点（提前想好答案）

1. **如果文档有几万篇，全量重建索引还可行吗？**
   → 不可行。改为增量索引：只对新增/变更文档做 embedding 和 upsert（存在则更新），
   删除时同步删向量；缓存按文档维度失效而不是全清。
2. **多轮对话支持吗？**
   → 当前是单轮。可扩展：把历史对话摘要加入 prompt，或给每条消息存 session 记忆。
3. **回答质量怎么保证？**
   → 建 QA 测试集评估命中率；调 chunk/top-k/prompt；检索不到时明确告知并引导换说法。
4. **为什么用 text-embedding-v3 而不是本地模型？**
   → 中文效果好、零部署成本；本地要装 torch（2GB+）。生产环境可权衡数据合规与成本。
5. **数据安全？**
   → 密码全部走 .env 不进 git；数据库账号最小权限；生产环境可上密钥管理。

## 五、项目局限与改进方向（诚实 + 上进）

- 单轮问答 → 可加多轮记忆（Redis 存会话）
- 答案流式输出 → SSE/WebSocket 提升体验
- 全量重建索引 → 增量 upsert + 文档级缓存失效
- 无鉴权 → 可加 API Key/登录
- 检索效果未量化 → 建评估集算命中率，调 chunk/top-k
